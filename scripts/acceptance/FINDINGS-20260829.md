# Runtime Failure Forensics + Durability Acceptance -- 2026-08-29

## RUNTIME_FAILURE_ROOT_CAUSE_CONFIRMED = YES

The reported symptom ("3 fresh ChatGPT dispatch requests never became Tasks;
quota status looked stale for 90+ minutes") is **not** a runtime/process
durability failure. Live telemetry (`runtime/scheduler-invocations/*.json`)
shows all 5 core Scheduled Tasks ticking `completed` continuously
throughout the reported window, and a *different*, well-formed request
created during this investigation (`adm-phase2-empty-checkpoint-evidence-
writer-repair-20260829-0442`) was admitted into a real `Task(status=ready)`
+ `Command` within ~6 minutes of being written to Drive -- proving the
admission pipeline was healthy the whole time.

**Real cause:** the 3 named requests --

- `adm-p0-dashboard-truth-visible-repair-20260829.json`
- `adm-p0-windows-autostart-manual-launch-20260829.json`
- `adm-p0-immediate-dispatch-wakeup-20260829.json`

-- were written to the Drive `DISPATCH-REQUESTS` folder with a **UTF-8
byte-order-mark (`EF BB BF`)** prefix before the opening `{`.
`manager/drive_dispatch_ingress.py`'s `read_request()` does
`raw.decode("utf-8")` (not `"utf-8-sig"`), which raises `UnicodeDecodeError`
on the BOM -- caught and converted to
`TaskError("Drive request is not valid UTF-8 JSON")` **before**
`request_id`/`project_id` are ever parsed out of the body.

Directly confirmed via the durable, file-id-keyed rejection registry
(`manager.dispatch_requests.dispatch_rejection_registry`) for all 3 files:

```
status: "rejected", reason_code: "ingress_rejected",
message: "Drive request is not valid UTF-8 JSON"
```

**Why it looked like the requests vanished instead of being rejected:**
because the failure happens before the body is parsed,
`annotate_partial_identity()` never runs, so the rejection is recorded
*only* under the Drive file_id, never under `(project_id, request_id)`.
`manager.dispatch_requests.resolve_dispatch_status_for_request()` -- the
only status surface a caller who just knows the human-readable
`request_id` can use (Dashboard/CLI/ChatGPT) -- reports these as
`dispatch_request_status: null, dispatch_request_read_failed: false`, i.e.
"never received." The rejection is real and durable; it is simply
invisible to anyone checking by request_id.

### Fix needed (handed to Claude A -- not applied by this branch)

Both changes are isolated to `manager/drive_dispatch_ingress.py` /
`manager/dispatch_requests.py`, not the Supervisor/runtime core:

1. **Primary**: decode BOM-tolerantly in `read_request()` --
   `raw.decode("utf-8-sig")`, or strip a leading `b'\xef\xbb\xbf'` before
   `json.loads`.
2. **Secondary** (visibility gap): best-effort recover `request_id` from
   the Drive filename (`metadata["name"]` minus `.json`, matching the
   `filename == f'{request_id}.json'` convention already enforced later)
   even when JSON parsing itself fails, so this whole rejection class also
   lands in the by-request-id registry.

Nothing needed from AG -- this is pure Python content validation, unrelated
to Scheduled Tasks / process durability.

### Secondary observation (not the root cause)

`manager.session_center`'s detached correlation child ran continuously from
`2026-08-29T02:58:52` local, tracking a 9-day-old execution
(`command-dispatch-chatgpt-claude-hands-off-e2e-20260820-080600z`), holding
port 8765 via `server.serve_forever()`. This is by design -- the child is
only killed when the supervisor's own `decide()` sees a newer non-terminal
command to switch to -- confirmed correct behavior, not a bug, but a good
target for the recovery checks below.

the single confirmed cycle for the slow-cadence components is representative,

**H (duplicate check):** `duplicate_overlap_detected: false` on every

`scheduler_invocation_id`s for the same task, plus direct live process-list

**I (timing):** every real recovered cycle exceeded the 60s target --
75-120s for the four ~1min-cadence tasks, and up to several minutes for
session_center_supervisor's own (occasionally very slow, cross-project)
tick. **Root mechanism, confirmed, not guessed:** none of these 5
components has any crash-triggered immediate re-invocation -- recovery
time is a direct function of "how long until the Scheduled Task's own next
periodic trigger actually runs," which is itself lengthened by
`MultipleInstances=IgnoreNew` skipping triggers while any previous instance
(even an unrelated slow one) is still alive. If sub-60s recovery is a real
requirement, the fix is either a shorter repetition interval or a
crash-triggered immediate re-trigger layered on top of the periodic one --
out of this branch's scope (Scheduled Task definitions are AG's lane), but
this is the exact, confirmed mechanism, not speculation.
